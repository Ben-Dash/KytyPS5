## Вывод

Эмулятор уже использует несколько CPU-потоков. Последовательная обработка гостевых
PM4-команд остаётся на одном основном CPU-потоке, но подготовка части работы,
компиляция и запись/отправка Vulkan-команд имеют отдельные рабочие потоки.

GPU получает работу через одну основную Vulkan-очередь. Это не означает выполнение
на одном GPU-ядре: очередь задаёт порядок подачи работы, а шейдеры выполняются
параллельно на устройстве. Даже одна очередь допускает перекрытие независимой
работы; соответствие очередей аппаратуре определяет драйвер.
[Контракт Vulkan queues](https://docs.vulkan.org/guide/latest/queues.html).

Сохранённые замеры указывают на два приоритетных направления: длинные остановки
создания новых pipeline и частые ожидания GPU при публикации/чтении гостевой памяти.
Это ещё не доказанный профиль игрового мира: подробные интервалы сняты при загрузке.
Обещать 60 FPS от добавления потоков по этим данным нельзя.

## Что действительно работает параллельно

| Участок | Реализация и проверяемое свидетельство | Ограничение |
| --- | --- | --- |
| Гостевые CPU-потоки | Native реализация pthread; это отдельный слой от GPU command processor | Их нагрузка и размещение по CPU-ядрам в игровом мире сейчас не измерены |
| Разбор гостевых graphics/compute PM4 | `GuestGpu` создаёт `Thread_Gpu`: `graphicsRun.cpp:196`, `:649` | Один основной поток обрабатывает состояние и зависимости команд |
| Запись и отправка Vulkan-команд | `CommandScheduler::EnableAsyncSubmit`, `SubmitThread`, `CommandStream`: `commandScheduler.cpp:699–746` | При deferred recording запись и submit обслуживает тот же worker, это не пул независимых recorder-потоков |
| Подготовка draw заранее | `drawSpeculator.cpp`, отдельный worker | Не заменяет упорядоченный основной путь и проверку актуальности ресурсов |
| Подготовка dispatch и компиляция | Lookahead, shader precompile, compute pipeline workers | На первом использовании возможен синхронный miss; увеличение workers расходует RAM |
| Выполнение GPU | Универсальная graphics+compute+present queue: `vulkanWindow.cpp:133–153`, `:430`, `:1398` | Общего разделения rendering graphics/compute по отдельным очередям здесь нет |
| Дополнительная transfer queue | Опциональный `KYTY_READBACK_QUEUE=1`, `vulkanWindow.cpp:433–472` | Предназначена для readback; не включена в записанных overrides последних запусков и не является готовым async-compute renderer |

На текущем ПК подтверждён Ryzen 9 5950X: 16 физических ядер / 32 логических
процессора. Записанный GPU — RTX 5060 Ti. Число доступных ядер не показывает
эффективность их использования: общего CPU/GPU utilization-профиля для той же
игровой сцены пока нет.

Последний c0 runtime прямо сообщает в `stdout.txt:55`:
`replayed 247 permutations on 7 threads` и
`queued 159 compute pipelines on 2 threads`.
Это прямое свидетельство многопоточной компиляции, а не замер загрузки всех CPU-ядер.

## Настройки, которые легко неверно интерпретировать

- `async_submit_enabled`, `record_thread_enabled`, `speculative_draws_enabled`,
  `dispatch_lookahead_enabled` уже включены по умолчанию в `emulatorConfig.h`.
  В последнем run.json переопределений, выключающих их, нет. Повторное включение
  этих параметров само по себе не добавит новую степень параллелизма.
- Последний запуск использовал `--pipeline-compile-threads 2`,
  `--pipeline-compile-threads-replay 1`, `--async-pipelines false`. Реальное число
  shader-module replay workers надо брать из лога, а не переносить значение одного
  pipeline-параметра на все пулы. Replay может использовать 7 workers, а отдельная
  graphics pipeline library при поддержке fast linking имеет 6 compile workers
  и 1 link worker (`pipelineLibrary.cpp:24–42`). Ограничение compute workers до 2
  не ограничивает все компиляторы процесса двумя потоками; нужен общий бюджет
  одновременно активных задач и памяти.
- `--async-pipelines true` сейчас допускает пропуск визуальных draw, пока pipeline
  не готов: `pipelineCache.cpp:2689–2697` возвращает null,
  `renderDraw.cpp:2952–2953` завершает draw без исполнения. Это не очередь,
  сохраняющая каждый draw для последующего точного исполнения. Рост FPS с такой
  настройкой нельзя принимать за решение задачи полной картинки/эффектов;
  для их проверки остаётся `false`.
- `ReserveCoreForCurrentThread()` вызывается на `Thread_Gpu`, но на Windows
  сразу возвращает, если отсутствует `KYTY_GPU_CORE`. При заданном значении он
  закрепляет этот поток за выбранным логическим CPU физического ядра, оставляя
  другим потокам остальные ядра (`threadSampler.cpp:350–395`). Это не закрепление
  всего эмулятора на одном ядре. В последних записанных overrides параметра нет,
  сообщения `gpu-core:` в проверенных логах нет. Полное унаследованное окружение
  старых процессов не сохранено, поэтому утверждение ограничено этими свидетельствами.
- `gpu_frames_ahead` существует в CLI/Config, но поиск по `src` не нашёл потребителя
  `GetGpuFramesAhead()`: только parser, поле, объявление и getter. Нельзя считать
  значение 0 причиной ожидания каждого кадра или предлагать значение 1 как уже
  работающую оптимизацию.
- `--screen-width 1920 --screen-height 1080` задаёт окно. В последнем подтверждённом
  игровом мире внутренние render targets доходили до 3840×2160. Пока нет
  подтверждения реальных внутренних 1920×1080; просто уменьшать guest backing
  ресурсов нельзя. 4K содержит вчетверо больше пикселей, но это не обещает
  четырёхкратный рост FPS при переходе на 1080p.

## Что говорят сохранённые замеры

Два полных 30-секундных интервала взяты из `drain-stats`, а не восстановлены по
выборочным сообщениям о медленных кадрах:

| Счётчик | Run 150515, 193 presents | Run 151125, 403 presents |
| --- | ---: | ---: |
| Full-drain wall / present | 21,61 мс | 29,07 мс |
| Tick-wait wall / present | 10,16 мс | 14,00 мс |
| GPU busy intervals / present | 23,35 мс | 30,57 мс |
| GPU gaps / present | 37,93 мс | 35,73 мс |
| Queue lock wait / present | 0,13 мс | 0,17 мс |
| Submissions / present | 58,95 | 75,34 |
| Readback events / present | 71,66 | 94,06 |

Источники: `stdout.txt:2686` первого запуска и `stdout.txt:3880` второго.
Основная доля full-drain wall приписана GPU-thread read fault во время
`R_RELEASE_MEM`: 78,86% / 74,34%; `WAIT_REG_MEM`: ещё 18,34% / 23,20%.
Небольшое ожидание queue lock не делает этот mutex первым кандидатом на переработку.

Категории ожиданий и GPU-интервалов перекрываются: складывать строки таблицы
в общий frame time нельзя. GPU busy здесь означает интервалы команд между
timestamp-замерами, а не occupancy всех shader multiprocessors. Presents
при загрузке также не равны измерению стабильного игрового FPS.

Текущая histogram обрезает длительности на 100 мс, а hitch-строки сохраняют только
кадры от 50 мс. Поэтому её p99/max=100 мс не исключает многосекундные остановки,
и по hitch-строкам нельзя восстановить честное среднее за последние 30 секунд.
Следующий benchmark должен сохранять необрезанные длительности всех кадров.

Отдельно обнаружены холодные pipeline misses: в run 150515 две новые compute
permutations ждут 18 061,3 и 16 864,2 мс (`stdout.txt:2772`, `:2792`). Они находятся
позже приведённого полного интервала. Это реальные большие остановки CPU в ожидании
компиляции, которые надо отделять от обычной стоимости кадра. В run 151125
синхронных pipeline builds/waits не зарегистрировано, но full-drain всё равно
29,07 мс на present: один только прогрев кэша не устранит весь источник тормозов.

60 FPS требует около 16,67 мс на кадр. Даже измеренные GPU-интервалы загрузки
превышают этот бюджет; их нельзя переносить на мир, но они не дают основания
обещать 60 FPS одной CPU-оптимизацией.

## Три варианта и порядок работы

### 1. Прогрев точных pipeline и уменьшение ненужных ожиданий GPU — первый выбор

Здесь уже есть прямые свидетельства затрат, а изменения можно делать постепенно.

Для холодного пути: собрать точные использованные specialization/permutation keys,
выяснить, почему они отсутствуют в replay/lookahead, и заранее создавать именно
нужные device pipelines. Shader module replay не гарантирует готовность каждого
pipeline. Сохранять совместимый driver cache/journal с проверкой source key,
планировать компиляцию с ограничением RAM. Увеличение threads без учёта памяти
сейчас может ускорить срабатывание memory guard. Асинхронный режим не считать
корректным решением, если ускорение получается от пропуска draw или fallback.

Для тёплого пути: добавить к существующей статистике причинные связи
guest address/range → последний GPU writer/tick → consumer/fault/label.
Проверить, где достаточно дождаться точного производителя или опубликовать
малый диапазон, а где полный drain действительно необходим.
`BufferCache::ReadMemory` уже использует `QueryReadback` и `Wait(state.tick)`
(`renderer/cache/bufferCache.cpp:648–676`); это не разрешение убрать ожидание.

До изменения поведения нужны ограниченные synthetic regressions: разные
CPU/GPU владельцы соседних диапазонов одной страницы, GPU write → CPU read,
CPU overwrite → GPU read, release label/timestamp, `WAIT_REG_MEM`, reuse/generation,
ошибка компиляции и однократное создание одинакового pipeline несколькими workers.
Тесты должны доказывать значения и порядок, а не просто меньший счётчик waits.

### 2. Несколько CPU workers для независимой подготовки/записи команд

Применять, если профиль покажет, что `Thread_Gpu` или worker записи расходует
значительную часть времени на CPU при простаивающем GPU. Сначала выносить чистые
вычисления и подготовку immutable draw/dispatch snapshots; общий mutable PM4 state
не распределять произвольно между потоками.

Для параллельной Vulkan-записи нужны отдельные command pools и descriptor pools
на workers, а затем упорядоченная отправка готовых результатов. Это требование
контракта внешней синхронизации Vulkan, а не добавление `std::async` вокруг текущего
общего recorder.
[Vulkan threading](https://docs.vulkan.org/guide/latest/threading.html).

Регрессии: переставленное завершение workers при сохранённом guest order,
повторное использование ресурса/descriptor generation, image-buffer alias,
CPU запись между подготовкой и исполнением, worker cancellation/error/cleanup.
Этот вариант сложнее первого и может вернуть прежние артефакты при неверных
снимках состояния или владении ресурсами.

### 3. Отдельные graphics/compute/transfer очереди GPU

Проверять после первых двух вариантов и только для работ с доказанной независимостью.
Второй `VkQueue` сам по себе не распределяет шейдер на дополнительные ядра.
Нужны доступные queue families, корректные timeline semaphore dependencies,
resource ownership/sharing и синхронизация guest graphics/compute ring.
Отдельная transfer queue может перекрыть копирование с независимым rendering,
но CPU всё равно ждёт copy, если сразу читает его результат.

Регрессии: compute → graphics чтение, graphics → compute запись, transfer → CPU
readback, shared resource reuse, alias/subrange hazards, unsupported-device fallback.
Сначала измерить реальное перекрытие на RTX 5060 Ti; больше очередей не гарантирует
больше аппаратного параллелизма. Это самый дорогой и рискованный вариант, поэтому
полная переделка scheduler сейчас не является первым шагом.

## Ближайший проверяемый план

1. Продолжать с чистых committed c0 исходников; архивированный sampler WIP использовать
   как материал диагностики. Новая попытка sampler требует корректного GPU fixture,
   независимых positive controls и coherence checks перед production-изменениями.
2. По сохранённым журналам разобрать два длительных sync pipeline miss и причины
   отсутствия готовых permutations. Подготовить воспроизводимую ограниченную модель
   очереди/кэша; не снижать качество изображения ради более высокого FPS.
3. Подготовить адресную диагностику read fault/release/wait, затем доказать конкретное
   избыточное ожидание регрессией. Не отключать обязательную синхронизацию.
4. Когда хватит RAM при работающем WSL, снять один bounded прогретый запуск в
   воспроизводимой сцене с нейтральным вводом. Проверить внутреннее разрешение,
   p50/p95/p99 по необрезанным frame times, cold misses отдельно, CPU активность критических потоков,
   waits, GPU gaps и рабочий набор памяти. Старый thread sampler не запускать
   одновременно на нескольких потоках: в коде прямо записан crash при таком режиме.
5. Если после уменьшения waits GPU голодает из-за CPU preparation/recording,
   проверять вариант 2; если доказана независимая GPU работа, проверять вариант 3.
   Менять по одному механизму и сравнивать ту же сцену с тем же кэшем и разрешением.

WSL по последнему прямому указанию пользователя оставляем работающим. Последний
game retry закончил работу по guard: 5,68 GiB свободной физической памяти,
2,5 GiB commit headroom, owned working set 14,21 GiB. Повторять неизменный запуск,
снижать guards или менять настройки памяти WSL ради замера не требуется.
