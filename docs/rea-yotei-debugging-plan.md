# REA для отладки Ghost of Yōtei

Проверено 2026-10-12 на native Windows. Исходники
[morluto/rea](https://github.com/morluto/rea) закреплены на
`3bdc8730bd98e073522bcb8ba86527be402c0cbe`, версия в `package.json` — `6.4.0`.
REA связывает агента с инструментами анализа бинарников; полезный для нас
путь — исследование CPU-кода, который формирует задания и данные для GPU.

## Что уже проверено

- Windows-бэкенд Ghidra принимает native PE x86/x64.
  [Проверка формата в исходниках](https://github.com/morluto/rea/blob/3bdc8730bd98e073522bcb8ba86527be402c0cbe/src/ghidra/GhidraProvider.ts#L302).
  Текущий `eboot.bin` имеет magic `4F153D1D`, то есть SELF; этот путь напрямую
  его не принимает. Linux-бэкенд поддерживает ELF/raw x86-64, но готовая
  проверенная поддержка PS5 SELF в исследованных исходниках не обнаружена.
- Node установлен. Ghidra, IDA и Hopper в проверенных локальных каталогах
  и PATH не найдены. REA setup, провайдеры и изменение MCP-конфигурации
  не запускались. Декомпиляция через REA пока не проверена.
  Проверенный Windows-путь требует Ghidra 12.1.x и full JDK 21+;
  [описание prerequisites](https://github.com/morluto/rea/blob/3bdc8730bd98e073522bcb8ba86527be402c0cbe/docs/windows-ghidra-p0.md).
- Выполнена конкретная подготовка существующим LLVM: ограниченный
  `llvm-readobj --file-headers --coff-debug-directory` на нашей свежей сборке,
  exit 0, около 66 мс. PE — AMD64, ImageBase `0x140000000`.
  SHA-256 исполняемого файла:
  `B048335F3F72D7EE90DB1EE976B0A496E324DD1BC8159D987A7D32ABA84390B0`.
- CodeView GUID/age совпали с PDB:
  `212256be-ae13-b96c-4c4c-44205044422e`, age 1.
  В map найдена `TileGetTextureBlockLayout`: RVA `0x49880`,
  статический VA `0x140049880`. Это небольшой известный объект для проверки
  адресов и качества будущего REA function dossier.
- Найден старый `_Build/analysis/yotei-eboot-extracted.elf`: ELF64 LE,
  FreeBSD ABI, x86-64, 39 278 468 байт, без таблицы секций. Файл датирован
  сентябрём; соответствие текущему SELF версии 1.512 не подтверждено.

Артефакты исследования, закреплённая копия исходников и PE/PDB-проверка:

## Текущий вопрос для исследования

Четыре проверенных переноса из peepostarexx/main уже сохранены в
`yotei-integration-native`: R8 SNORM, повторное использование packed offsets,
BC-R64 и начальное число активных вершин NGG. Подробные RED/GREEN и проверки
соседних случаев — в [launch plan](ghost-of-yotei-windows-plan.md).

Последний запуск со всеми четырьмя исправлениями показал растянутую геометрию,
около 3 FPS в диагностическом окне. Внутренние цели всё ещё доходят до 4K,
хотя окно задано 1920×1080. Стабильная картинка и ~60 FPS не достигнуты.

Теперь есть точная связь compute- и vertex-снимков: используемые vertex-шейдером
строки матриц 2097/2098 в плохой палитре были нулевыми ещё до захваченных
compute-dispatch и остались такими после них. Эти dispatch обрабатывали другие
строки. В другой палитре соответствующие строки конечны; отдельные producer
действительно заполняют матрицы. Потеря ненулевых данных между этими снимками
не подтверждена.

Поэтому следующий вопрос: какое задание должно формировать именно нужные строки,
с какими входными данными и условиями исполнения? REA может помочь исследовать
CPU-сторону этого вопроса. Проверка RDNA, SPIR-V, масок волн и GPU BDA остаётся
в нашем специализированном декодере, трассировке и регрессионных тестах.

## Вариант A: сразу использовать текущие захваты и LLVM

1. Дополнить диагностический отбор dispatch условием покрытия нужной строки.
   Размер SRD 124224 уже проверяется до расходования квоты; теперь надо выбрать
   задания, у которых фактический интервал выходных индексов включает 2097/2098.
   Для исследованных producer выходная база — flat SRT `0xc4`, число заданий —
   `0x17`; учитывать реальный размер dispatch и дополнительные условия пути.
   Это отбор диагностических данных, а не изменение поведения игры.
2. Сохранить оба соседних банка, входные buffers, raw roots, bound flattened SRT,
   EXEC и BDA page/fault сведения. Первый банк: child+56 → slot2/flat12;
   второй: child+120 → slot25/flat188. Флаг `0xc5` относится ко второму банку.
3. Сравнить плохой и конечный случаи по тем же адресам и заданиям. Отдельный lead:
   в одном задании count349 первые64 строки остаются нулевыми, остальные285
   заполняются; в другом заполняются все349. Сначала проверить входы и страницы,
   затем маски волн. Ноль сам по себе не является доказательством дефекта.
4. По найденной семантике сделать независимый минимальный RED, исправить общий
   механизм, пройти тот же GREEN и соседние случаи, затем повторить игру.

Этот вариант не требует подключения нового движка и продолжает уже проверенную
цепочку доказательств.

## Вариант B: подключить REA для целевого CPU-анализа

1. Подготовить локальный Ghidra-провайдер и ограниченную рабочую директорию.
   Использовать CLI; глобальная регистрация MCP для первого опыта не нужна.
   [Native CLI](https://github.com/morluto/rea/blob/3bdc8730bd98e073522bcb8ba86527be402c0cbe/docs/cli.md#native-analysis).
2. Первым опытом взять собственный PE с проверенными PDB/map. Получить досье
   одной известной функции и её references, сверить адрес и смысл с исходником.
   Это проверяет инструмент; результат не считается исправлением эмулятора.
   Автоматическая загрузка PDB через REA отдельно не проверена; map остаётся
   независимым эталоном адресов для этого опыта.
3. Для закрытого CPU-кода игры сначала подтвердить происхождение ELF или
   экспортировать ограниченный участок из текущего загруженного образа с точной
   базой, relocation/ABI сведениями. Затем выбрать провайдер, принимающий этот
   формат. Старый ELF не считать автоматически соответствующим текущей игре.
4. Исследовать только найденные функции формирования bone jobs/SRT roots:
   запись count, output base, двух SRD и условий запуска. Сопоставить вывод
   с реальными снимками; декомпилированная гипотеза требует отдельной проверки.

Критерий полезности REA: оно объясняет конкретное значение входных данных или
условие producer, которое наши захваты не объясняют, и даёт проверяемый
минимальный случай. Импорт всего бинарника без такого вопроса откладывается.

## Быстрота следующих итераций

- Фиксы собирать пачкой после отдельных регрессий; исходники замораживать на
  время одной native-сборки, сохранять совместимые кэши и исходные captures.
- Испытан preset `pipeline-compile-threads=4`, replay=1. Ускорение не доказано
  равным A/B; прошлые большие задержки относятся главным образом к driver
  compilation новых pipeline, а CPU replay занимал около 0.55 с.
- Разделение compatibility key непрозрачного Vulkan cache и строгого ключа
  compiler/journal — отдельный кандидат ускорения разработки. Нужны проверки
  заголовка, смены SPIR-V/layout и реального GPU readback; обход текущего ключа
  не применяется.
- Сначала стабильные пиксели и корректные данные; затем отдельный прогретый
  замер фактического 1080p без тяжёлых snapshot-drains.
